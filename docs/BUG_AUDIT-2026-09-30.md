## Confirmed bugs

### B01 — Invalid current-version imports crash startup

**Files:** `src/save/storage.ts:177` (`parseImport`), `src/sim/GameState.ts:483` (`migrate`, especially its final version-only cast), `src/ui/menu.ts` import handler.

**Reproduce through the game:**

1. Create a JSON file containing only `{"version":21}`.
2. Title screen → Load park → Import a save file.
3. Select that file. If all three slots are occupied, choose Replace to reach the same startup path.

**Observed:** Import validation accepts the file. The title menu disappears, gameplay does not start, and Chrome reports `Cannot read properties of undefined (reading 'length')`. No useful import error appears. See `logs/audit-interactions.log` and `incomplete-import.png`.

**Minimal simulation reproduction:** `parseImport('{"version":21}')` returns a `state`; `new Simulation(state).step()` throws.

**Expected:** Reject missing/invalid fields before hiding the menu or attempting to start a park. Present an understandable import error and keep existing parks accessible.

**Why:** `migrate()` accepts any object with the current version as `GameState`; no runtime shape validation follows migration. `parseImport()` catches parsing/migration exceptions, but later startup exceptions happen outside that catch.

**Review/fix direction:** Validate migrated state shape, map dimensions/array lengths, scenario/species identifiers, required collections and numeric values before acceptance. Also inspect `loadSlot()`/`revive()` because they share this migration path. Validate both bare-state and full-record imports. This audit confirmed a startup failure, not destruction of another saved park.

### B02 — Construction ignores existing jeep tracks

**Files:** `src/sim/paths.ts:17` (`tileOccupant`), `src/sim/commands.ts:124` (`pondDigBlocker`), `planPaths`, `placeBuilding`, `placeFeeder`, `placeDecor`.

**Reproduce:** On owned grass, build jeep track at `(10,10)`. Separately try each:

- Build a visitor path on `(10,10)`.
- Build a path at `(11,10)`, then a restaurant on `(10,10)`.
- Dig a pond at `(10,10)`.

**Observed:** All three actions succeed, and the track bit remains `1`. A path and track occupy the same tile; a building occupies a track tile; or a pond contains active track. The reverse order is inconsistent: placing track on an existing path is rejected.

**Expected:** Define and enforce occupancy consistently. Ordinary paths/buildings/pond digging should reject existing track or explicitly remove/replace it with correct costs and cleanup. The current track shop description says tracks run alongside paths.

**Why:** `trackBlocker()` checks paths, but the common occupancy helper and the other construction blockers never check tracks.

**Evidence:** `AUDIT B02` in the archived simulation probes. The three branches are tested independently. Feeder/decor overlap is a source-review follow-up suggested by the shared helper; it was not separately exercised in this reproduction.

**Regression checks:** Test both construction orders, demolition, refunds, and a station with riders when its track is replaced.

### B03 — Moving a dinosaur bypasses visitor-enclosure cleanup

**Files:** `src/sim/commands.ts:139` (`dinoSpotBlocker`), `:224` (`moveDino`), and the cleanup in `buyDino`.

**Reproduce:**

1. Make a concrete enclosure `(2,2)` to `(7,7)` and buy a Protoceratops into it.
2. Make another empty enclosure `(10,2)` to `(16,8)`.
3. Put a visitor path at `(12,4)` and a restaurant at `(13,4)` in the empty enclosure.
4. Move the existing dinosaur to `(12,4)`.

**Observed:** Move succeeds, the dinosaur lands on the path, and both the path and restaurant remain. Buying a dinosaur into an empty enclosure clears its paths; moving one does not.

**Expected:** Moving should apply the same enclosure-conversion/placement rules as buying. Resolve visitor infrastructure consistently before the enclosure becomes occupied by an animal.

**Why:** `moveDino` calls the habitat/paddock blocker and assigns coordinates; it never performs the path cleanup present in `buyDino`. The blocker also does not reject infrastructure occupants.

**Evidence:** `AUDIT B03`. This confirms retained infrastructure, not a demonstrated visitor injury. Review buying directly onto buildings/feeders as a related placement-validation edge case.

### B04 — Fence repair goals report 100% despite broken fences

**Files:** `src/sim/goals.ts:52` (`fencesOkPercent`), `src/sim/fences.ts` (`fenceAt` versus `fenceTypeAt`).

**Reproduce:** Build a 5×5 concrete fence box (20 segments). Set 10 built segments to zero HP, leaving the other 10 at full health. Read `fencesOkPercent(state)`.

**Observed:** **100%**, instead of **50%**. `allFenceEdges()` includes built broken segments, but `fencesOkPercent()` skips them because `fenceAt()` returns zero for broken fences.

**Expected:** A broken built segment counts as needing repair. Use built fence type/identity for the denominator, and HP for the healthy numerator.

**Impact:** Repair progress and challenge medal eligibility can be wrong precisely when repairs matter most. Great Escape and Fire Mountain repair goals use this function.

**Evidence:** `AUDIT B04`.

**Regression checks:** Mixed intact/broken segments, all segments broken, low-but-nonzero HP, and genuinely no built fences. The all-broken result is a source-derived consequence of the same filter, not a separate measured case here.

### B05 — Flood-broken fences can leave cached enclosures stale

**Files:** `src/sim/systems/flood.ts:149` and `:168`; `src/sim/Simulation.ts` (`regions`, `worldRevision`).

**Reproduce:** The archived probe sets up a grass enclosure beside a river, a single low tile already flooded at level 3, and a one-HP wooden fence on that tile's edge. At Flood Season hour 34, run `hourlyFlood()` while recording `invalidateWorld()` calls. Keep the wet tile count and level unchanged.

**Observed:** The fence drops to **0 HP**, but the flood system calls `invalidateWorld()` **zero times**.

**Expected:** Breaking an intact fence must invalidate the world/region cache even when water coverage is unchanged.

**Why:** Flood invalidation depends on water level or wet-list length. The fence rot loop mutates HP without detecting a transition to broken. In contrast, ordinary wear and worker repair explicitly invalidate when a fence changes connectivity.

**Impact:** Cached paddock/public classification can disagree with the real fence layout until some later world invalidation. That effect follows from the verified missing invalidation and `Simulation.regions()` cache; the probe directly measures the break and invalidation count rather than a full visitor/escape sequence.

**Evidence:** `AUDIT B05`.

**Regression checks:** Warm the region cache, break a boundary during a steady flood, compare cached versus freshly computed regions, and verify escape detection on subsequent steps. Also review water coverage that changes membership without changing length.

### B06 — Safari jeeps ignore floodwater

**Files:** `src/sim/systems/rides.ts:28` (`onTrack`), `stepJeeps`, and station creation.

**Reproduce:** Build a station beside a two-tile track at `(10,10)` and `(11,10)`. Spawn its jeep, mark both track tiles flooded, set it touring, then run one jeep step.

**Observed:** `onTrack()` returns true for a flooded tile, and the jeep moves from `(10,10)` to flooded `(11,10)`.

**Expected:** Suspend/evacuate affected safaris or prevent movement into flooded tiles. Choose an explicit safe unloading behavior for existing riders.

**Why:** The track predicate only checks the track bit. Attraction boarding checks flooded buildings, but driving does not check flooded track; a dry station can serve a route through wet ground.

**Evidence:** `AUDIT B06`. Direct movement is confirmed. This does not establish a crash or animal/visitor loss.

**Regression checks:** A dry station with a flooded route, a flooded station, mid-tour flooding, flood drainage, and riders whose original boarding path is now wet.

### B07 — Challenge success precedes fatal-loss enforcement

**Files:** `src/sim/goals.ts:197` (success branch), `:224` (`loseIf` branch).

**Reproduce:** Create Great Escape state. Set its round to Gold, reputation to 80, best-day visitors to 100, lost dinosaurs to 4, and hours to 16 (midnight on this game's calendar). Run `hourlyScenario()`.

**Observed:** Status becomes **`won`**, even though Great Escape's fatal loss threshold is **more than 3**. The success branch returns before the loss check.

**Expected:** A fatal scenario condition prevents awarding a medal/win at that evaluation. Preserve whatever timing is intended for loss checks, but apply their precedence consistently.

**Impact:** A park that should lose can receive medals and unlock another challenge. The same ordering also precedes bankruptcy/deadline checks; those interactions need review rather than assuming their intended policy.

**Evidence:** `AUDIT B07`. This uses constructed final-round state to isolate precedence; it is not a claim that a normal unassisted playthrough was observed reaching these exact simultaneous values.

**Regression checks:** Goals met at the same evaluation as a fatal loss; Bronze/Silver as well as Gold; deadlines; bankruptcy. Clarify whether hard loss conditions should be evaluated hourly or only at midnight.

### B08/B09/B10 — Dialogs resume a game that should remain paused

These are **one shared pause-management bug group**, reproduced at three separate call sites/interactions.

**B08: Pause menu loses explicit Pause.** Click the HUD Pause button (speed 0), open ☰, then Resume. Speed becomes **1**. Expected: closing an overlay restores the prior speed, including 0. `src/ui/overlays.ts:33` assigns `resumeSpeed = sim.speed || 1`.

**B09: Decision card loses explicit Pause.** In the dev browser, pause the sim, assign a pending fundraiser choice, and emit a change with `sim.setSpeed(0)`. Dismiss it with Decide later. Speed becomes **1**. Expected: the player's pause remains. `src/ui/choice.ts:26` only remembers nonzero speed, leaving its default or previous resume value; `close()` then resumes.

**B10: Overlapping dialogs independently resume.** Open a decision, then show an outcome using the exported `showOutcome()` helper. Both overlays are open and speed is 0. Dismiss the outcome. The decision remains visible but speed becomes **1**. Expected: the park stays paused while a pausing decision is open. See `src/ui/overlays.ts:103` and `src/ui/choice.ts:43`.

**Evidence:** `logs/audit-interactions.log` shows all three actual browser speed values. B09/B10 use explicit dev setup to reliably create the pending choice/overlap; B08 uses menu interaction. Saved pending decisions were also tested: after normal initial ticking they correctly reopened and paused, so this report does **not** classify their brief initial delay as a separate bug.

**Fix direction:** Coordinate pause ownership and saved speed rather than letting each overlay unconditionally resume. Review dig, briefing and outcome dialogs together. Preserve explicit pause across closing, saving, deciding later, and nested overlays.

**Regression checks:** Prior speeds 0/1/3/8; pause-menu Resume and Save; dig Skip/Done; choice answer/Decide later; milestone/outcome; two overlapping pausing overlays. Use actual event ordering for the permanent overlap test, in addition to the direct helper reproduction.

### B11 — Flood rot is applied twice to shared fence edges

**Files:** `src/sim/systems/flood.ts:168` (`tileEdges` loop and `ROT_PER_HOUR`).

**Reproduce:** Put a full-health wooden fence between two low grass tiles connected to a river. Both tiles flood at level 3. Run one `hourlyFlood()` call at hour 34.

**Observed:** Fence HP becomes **94**. The stated flood decay is `3 / strength` per hour; strength 1 would give **97** after one application.

**Expected:** Apply the documented decay once per wet built edge per hour, or explicitly define a different two-sided rule and update its presentation/tests.

**Why:** Every flooded tile loops over all four adjacent edges; the edge shared by two wet tiles is processed twice.

**Evidence:** `AUDIT B11`.

**Regression checks:** One wet side versus two wet sides, strengths 1–4, zero-HP edges, sandbag immunity, and connectivity invalidation when rot breaks a fence (B05).

## Challenge rule needing review

### B12 — Selling every escapee earns the rescue medal

**Files:** `src/sim/goals.ts` (`dinosHome` returns 100 when no animals remain), `src/sim/commands.ts` (`sellDino`), Great Escape Bronze goals.

**Reproduce:** Start Great Escape, sell all 14 escaped grown-up dinosaurs using normal `sellDino` commands, then evaluate `hourlyScenario()`.

**Observed:** Zero dinosaurs remain, and Bronze is awarded immediately. No animal was returned to a paddock. No loss statistic is charged for a sale.

**Review:** This is a confirmed shortcut, but whether selling counts as an acceptable rescue is a product rule. The challenge's wording says every dinosaur should be back in its paddock. If that is intended literally, track the original animals/rescues or require an appropriate remaining population; avoid globally rejecting empty-state goals without checking other scenarios.

**Evidence:** `AUDIT B12` logs `sold all 14 animals; Bronze awarded; rescued zero`. Review selling animals before disasters separately; this audit does not assume selling to another park should always count as a loss.

## Test-script problems discovered during the audit

These are QA tooling issues, separate from the gameplay findings. Corrections were made **only in the isolated audit copy**, so the next model should review them for the original repository.

1. **Encoded screenshot paths:** scripts use `new URL('.', import.meta.url).pathname`. Under a path containing spaces, the resulting `%20` directory does not exist and screenshots fail with ENOENT. The audit decoded the pathname; prefer Node's `fileURLToPath()` for a permanent fix.
2. **Obsolete shop selectors:** `habitats-check` searches for `[data-decor="pond"]`; `attractions-check` searches for `#path-picker`; `repro-place` assumes tool buttons enter placement immediately. Current tools open picture shops. The audit used `.shop-card[data-id]` choices/current visible sheet, and completed the placement flow.
3. **Incomplete unlock fixture:** `challenges-ui` only unlocks Great Escape before trying Money Pit. Money Pit now requires Fire Mountain and Flood Season medals. The audit provided the current predecessor records.
4. **Incomplete visitors fixture:** `items-check` injects visitors without `rode`/`riding`, causing `stickers.ts` to throw. The audit added the required fields; corrected run had no page errors. This was not reproduced with normally spawned visitors.
5. **Anonymous dynamic modals:** `sheet-scroll` enumerates IDs, but generated shop modals have no ID, then `getElementById('')` returns null. The audit assigned temporary IDs for inspection.
6. **Weak pass criteria:** many scripts print page errors or zero-action results while exiting successfully. Add explicit assertions for expected state changes and nonzero exit on unexpected page errors. For example, `care-check` printed `Chomp loves that!` for its intended hungry-carnivore pat; that browser log alone does not verify it selected the carnivore, although the pure care tests cover the rule.
7. **Challenge balance coverage:** the Fire Mountain strategy case only asserts at least Bronze, Flood Season at least Silver. The handoff's generic “sensible play wins” description overstates their asserted coverage. Gold completion needs an explicit end-to-end balance run for those two challenges.
